What it does

Three kinds of people use the same app, and the app shows each of them a different slice of the same data.

An employee checks in and out, applies for leave, claims expenses, reads their payslips, tracks goals and uploads documents. A manager sees all of that for themselves, plus their team's leave and expense requests, which they approve or reject. An admin (HR) sees everyone, adds and deactivates employees, fixes attendance, enters payslips, and maintains the holiday calendar and announcements.

On top sits Disha, a chat button in the corner of every screen. Ask "how many casual leaves do I have left?" and it queries the database; ask "how much notice for earned leave?" and it reads the company policy; ask for a colleague's salary and it refuses. The rest of this page is mostly about how that last sentence is guaranteed rather than hoped for.

The choices are deliberately boring below the agent: one database file, no ORM models, no state library in the browser, no build step beyond Next's own. Everything interesting is in who is allowed to see what.

A request, end to end

The browser only ever talks to the Next.js server. It forwards /api/* to FastAPI, which keeps the session cookie same-origin — that is what makes the app work unchanged from a phone on the same Wi-Fi.

Authentication is one lookup: the cookie carries a random token, the sessions table maps it to a user row, and that row is passed into every handler. There are no roles in the token and no client-side permission logic — the server decides, every time.

Who can see what

This table is the app's core rule. The assistant inherits it exactly; it is not re-implemented for chat.

Note the deliberate gap: a manager approves their team's leave but cannot see their team's salary or daily attendance. Approving a request needs the request, not the person's pay.

The Disha agent

A question does not go straight to a language model. It passes a gate, gets classified, and only then touches data — and only the kind of data the question actually needs.

Each answer carries its route and the steps it took, and the chat panel prints them under the reply — conversational policy data blocked — so nobody has to guess whether a number came from the database or from a document.

The SQL sandbox

Letting a language model write SQL against an HR database is the riskiest idea in this app. One loose query returns everyone's salary. Here is why it can't.

The model never sees the real tables. Before its query runs, the connection is given a set of temporary views that already contain only the rows the asking person may see — and the query is checked against a whitelist of those view names.

Two details matter more than they look. The sandbox takes a connection that is never reused, so its temporary views cannot leak into the next request — an early version of this had exactly that bug, and an ordinary API call could have been served the previous person's view. And a regular employee who asks about someone else by id gets an explicit not allowed, rather than silently receiving their own figures, which is how a wrong answer becomes a confident wrong answer.

What the tests pin down

backend/test_agent.py asserts that SELECT * FROM users, DROP, PRAGMA, two statements, and sqlite_master are all refused; that an employee querying payslips sees one row and a manager sees their team's leave; and that the real tables are untouched afterwards. It runs without calling OpenAI.

Data model

Ten tables, all hanging off users. Anything an employee owns carries a user_id, and that single column is what every permission rule keys on.

TableHoldsWorth knowing
usersPeople, role, department, manager_idSelf-referencing: the reporting line is one column
attendanceOne row per day workedNo row means leave, holiday or absence
leavesRequests, type, days, statusdays counts working days; quotas CL 12 / SL 12 / EL 15, LWP unlimited
expensesClaims + receipt bytesSame approval path as leave
payslipsBasic, HRA, allowances, deductionsGross and net are computed, never stored
goals, documentsPer-employee itemsFiles live in the database, capped at 7 MB
holidays, announcementsCompany-wideHolidays make leave skip those days
sessionsLogin tokensDeleted on password change

A balance is never stored. "9 casual leaves left" is always quota − (approved + pending) computed at read time, which is why a pending request already holds its days.

Running it

cd backend && python -m uvicorn app.main:app --reload   # API on :8000
cd frontend && npm run dev                              # app on :3000

python -m app.seed                 # 20 employees with a year of records
python -m app.knowledge --wipe     # index data/policies into Qdrant
python test_agent.py && node ../test.mjs   # both suites

Secrets come from backend/.env: OPENAI_API_KEY is required for chat, QDRANT_* for policy answers, LOGFIRE_TOKEN for tracing. Each is optional in the sense that the app degrades rather than crashes — without Qdrant, Disha says it can't find the policy; without a model key, the chat panel reports it isn't set up, and the rest of the app is unaffected.

Seeded logins are firstname.lastname@company.com with the password password123 — sneha.iyer is a regular employee, rahul.sharma manages six people.

Shipping it

Every push to main runs one GitHub Actions pipeline, and each stage only starts if the one before it passed. A pull request stops after the first two, so nothing reaches the server until it is merged.

1 test       test_agent.py, test_knowledge.py, test.mjs, frontend build
2 evaluate   seeded API + the golden questions, compared with the baseline
             a safety drop blocks; a quality or latency drop warns
3 push       backend and frontend images to AWS ECR, tagged with the commit
4 deploy     SSH to the EC2 box, docker compose up, health check over HTTPS

On the server, Caddy terminates HTTPS (a Let's Encrypt certificate it renews itself) and passes requests to the Next.js container, which proxies /api/* to FastAPI exactly as in the diagram above. SQLite lives on a Docker volume, so it survives redeploys. Keys reach the server from GitHub secrets at deploy time; none are in the repository.

The evaluate stage runs only the checks that need no judge (route, the number in a data answer, safety refusals, reliability, latency), because they give the same result every run. The judged quality scores stay a local, five-run exercise: one judged run moves too much to gate on.

Not built yet — and why that's written down

  • Disha cannot act. It reads. Applying for leave or approving a request from chat needs a confirmation step that doesn't exist yet.
  • No payroll tax engine. Payslip figures are entered by HR; PF and professional tax are modelled, income tax is not.
  • The chat rate limit is per process. Eight questions a minute and fifty an hour per employee, counted in memory — correct for one API worker, and it needs a shared counter before running several.
  • The eval set is small. Twenty-one golden questions, scored on every run: route, the number in a data answer (checked against the database), safety refusals, and DeepEval's faithfulness, relevancy, contextual precision/recall and correctness. It catches regressions; it is not broad coverage yet.
  • One server, one file, no backup yet. SQLite on a single EC2 volume is fine for a few hundred employees, but losing that disk loses the data. PostgreSQL (or a nightly copy to S3) is the next operational step, and a settings change in the app.
  • The SQL writer is not perfectly consistent. On the golden set it gets roughly one data answer in sixty wrong, by writing a query that is valid but asks the wrong thing. The sandbox makes that a wrong number, never a leak, and the eval gate catches it when it repeats.

The sample policies in data/policies/ are written to match the app's real behaviour, but they are samples. Replace them with the approved versions before anyone relies on an answer.
